No reemplaza la [arquitectura propuesta](02-arquitectura.md), el [análisis DDD](07-ddd.md) ni las [ADR](08-adr.md); los referencia y no duplica su contenido.

## 1. Propósito y convención

El método de documentación acordado es **ADR + C4 + SRS** ([05 — Progreso y decisiones](05-decisiones.md), DL-004). Este documento cubre la parte C4: un modelo de componentes y tres vistas de componentes.

La decisión DL-005 fija una convención deliberadamente acotada:

- **Solo diagramas de componentes.** No se crean diagramas C4 de contexto, contenedores, despliegue ni código.
- **Una sola vista sirve para software y recursos cloud.** Los recursos cloud se representan como componentes con un matiz visual; no hay un diagrama de despliegue separado.
- **Actores y sistemas externos** se muestran en la misma vista: los sistemas se modelan como componentes externos y los actores como personas.
- **El MVP es local.** Los recursos cloud son candidatos futuros u opcionales, no implementados. El modelo no afirma que existan cuentas, servicios contratados ni infraestructura desplegada.

### 1.1 Matiz local / cloud / externo

| Tipo | Representación | Etiqueta Structurizr | Estereotipo PlantUML |
|---|---|---|---|
| Componente del MVP local | Fondo claro, borde continuo | `Local` | `<<local>>` |
| Recurso cloud candidato | Fondo azul claro (`#E6EEFF`), borde discontinuo azul (`#1A53FF`), icono ☁ en PlantUML | `Cloud` | `<<cloud>>` |
| Sistema externo futuro | Fondo gris, borde continuo | `External` | `<<external>>` |
| Actor humano | Figura de persona | `Person` | `<<person>>` |
| Componente | Elemento base del modelo | `Component` | `<<component>>` |

La leyenda de cada `.puml` repite esta convención. Una relación discontinua y azul indica una **alternativa futura o sustitución no implementada**, no tráfico real.

La tecnología de diagramas es **Structurizr DSL** como fuente del modelo y **PlantUML** para renderizar (DL-006).

### 1.2 Fuente del modelo y artefactos

| Artefacto | Rol |
|---|---|
| [`diagrams/workspace.dsl`](diagrams/workspace.dsl) | Fuente Structurizr del modelo: personas, sistemas externos, componentes, relaciones y vistas `operacion`, `ingesta` y `reconciliacion`. |
| [`diagrams/c4-operacion.puml`](diagrams/c4-operacion.puml), [`c4-ingesta.puml`](diagrams/c4-ingesta.puml), [`c4-reconciliacion.puml`](diagrams/c4-reconciliacion.puml) | Vistas C4-PlantUML mantenidas a mano para la leyenda, el icono cloud y el layout. |
| `diagrams/out/` | SVG renderizados con `plantuml -tsvg`. |

El DSL es la fuente de los elementos y las relaciones. Los `.puml` son la capa de presentación: si cambia un componente, una relación o una vista, se actualiza primero el DSL y después el `.puml` correspondiente. La exportación automática de Structurizr sirve como referencia: conserva colores y bordes del modelo, pero no reproduce la leyenda ni el icono ☁ de estos diagramas.

La agrupación **“MVP local”** del modelo es lógica: permite una sola vista de componentes y no afirma que todo corra en un único proceso. El simulador es un proceso aparte; la base y el broker se levantan con Docker Compose ([02 — Arquitectura](02-arquitectura.md), §8).

## 3. Catálogo de componentes

### 3.1 Actores

| Actor | Necesidad en el MVP | Contexto DDD | Requisitos |
|---|---|---|---|
| Planificador de corto plazo | Crear y publicar el plan de turno; revisar cumplimiento | Planificación; Reconciliación | FR-PLAN-01/02, FR-REC-01/02 |
| Despachador | Seguir flota, colas, estado y alertas | Operación | FR-MAP-01, FR-FLT-01, FR-ALR-01 |
| Operador de chancado | Ver alimentación, throughput, tolva y paradas | Chancado | FR-CRU-01/02 |
| Supervisor de turno | Revisar KPIs, plan vs real y replay | Reconciliación; Operación | FR-REC-01/02, FR-RPL-01, FR-ALR-01 |
| TI/OT | Diagnosticar salud, flujo y errores de datos | Ingesta y observabilidad | FR-DF-01/02/03 |

El alcance y el SRS mencionan otros roles (ingeniero de perforación y voladura, operador de equipo, gerencia de operaciones). No se modelan como componentes separados en esta iteración para no duplicar actores: perforación/voladura y gerencia quedan cubiertos por FR-DRILL-01 y FR-REC-03, y el operador de equipo no tiene vista propia porque la operación es simulada. Pueden incorporarse si una vista futura lo requiere.

## 4. Mapeo a los contextos de `07-ddd.md`

| Contexto DDD | Componentes C4 | Lectura |
|---|---|---|
| Planificación de turno | `web`, `api`, `recon` (retroalimentación), `db` | El plan se crea y publica por la API; la reconciliación alimenta la siguiente versión. |
| Operación de mina | `ingest`, `twin`, `ws`, `web`, `sim`, `db` | El estado operativo se proyecta desde eventos; el simulador produce la operación sintética. |
| Chancado primario | `sim`, `ingest`, `twin`, `ws`, `web`, `db` | La telemetría y las paradas del chancador se proyectan y se muestran; no hay componente de control. |
| Reconciliación | `recon`, `db`, `api`, `web` | El cierre y el snapshot oficial viven en Reconciliación; la API y la web los exponen. |
| Ingesta y observabilidad | `ingest`, `broker`, `twin` (alertas), `db`, `observability` (futuro), `managedBroker` (futuro), TI/OT | La ingesta valida y ordena; el motor de alertas está en el gemelo; la salud se calcula en el servidor. |
| Simulación | `sim`, `broker`, `db` (metadatos de corrida), `web` (selector) | El simulador es un proceso aparte y reemplazable por fuentes reales. |
| Catálogo de sitio | `db` (tablas maestras), `api` | No hay un componente de catálogo separado: son datos maestros y API, como propone 07. |

**Contexto no es componente.** Un componente puede servir a varios contextos (`web`, `api`, `db`) y un contexto puede ocupar varios módulos. El MVP sigue siendo un monolito modular (ADR-001); los límites de 07 son límites de modelo y de propiedad de datos, no unidades de despliegue. La vista de componentes no crea microservicios ni un servicio por contexto.

## 5. Relación con ADR-008 a ADR-014 y brechas P0

Las siete ADR están en estado **Propuesto**; ninguna está aceptada. Los diagramas muestran responsabilidades previstas, no decisiones cerradas. Si una ADR se rechaza o cambia, el componente afectado y sus relaciones deben revisarse en `workspace.dsl` y en los `.puml`.

| Brecha | ADR | Componentes implicados | Efecto en el modelo |
|---|---|---|---|
| P0-01 | ADR-008 — reloj simulado | `sim` (reloj y aceleración), `ingest` (`receivedAt`), `twin` (alertas con dominio temporal), `api`/`ws` (exposición), `web` (reloj dual), `db` (tiempos) | El reloj no es un componente aparte; es una responsabilidad distribuida entre simulación, ingesta, interfaz y persistencia. |
| P0-02 | ADR-009 — identidad y orden | `sim` (`eventId`, `runId`, `seq`), `ingest` (deduplicación, huecos, reordenamiento), `db` (índices únicos), `twin` (proyecciones ordenadas), `api` (replay) | La deduplicación persistente vive en `ingest` + `db`; no se modela una cola adicional. |
| P0-03 | ADR-010 — fuente de verdad | `ingest` (única puerta de hechos), `twin` (proyecciones y KPIs en vivo), `recon` (KPIs oficiales), `db` (log, telemetría y snapshots), `api`/`ws` (lectura) | Los derivados (`kpi.snapshot`, `alert.*`, `data_source.health`) no vuelven al broker; por eso no hay flecha de `twin` o `recon` hacia `broker`. |
| P0-04 | ADR-011 — turno y corrida | `api` (crea y cierra el turno), `sim` (corrida), `recon` (cierre), `db` (`simulation_runs`), `web` (controles) | El turno no es un componente: es estado y ciclo de vida repartido entre API, simulador y reconciliación. |
| P0-05 | ADR-012 — versionado del plan | `api` (versiones), `web` (plan base vs ajuste), `sim` (consume la versión vigente), `recon` (plan base), `db` (plan versionado) | La reconciliación se apoya en `recon` y en el plan persistido; no se agrega un componente de planificación separado. |
| P0-06 | ADR-013 — clasificación ore/waste | `sim` (clasificación propuesta en el carguío; el alcance la sitúa en la descarga), `ingest` (valida material y destino), `twin`/`recon` (tonelaje y desvíos), `web` (vistas), `db` (`dig_units`, `destinations`) | La clasificación es una regla de dominio y de simulación; no un componente nuevo. Decisión abierta. |
| P0-07 | ADR-014 — KPIs, alertas y parámetros | `twin` (KPIs y motor de alertas), `recon` (KPI oficial), `sim` (parámetros y escenarios), `db` (versiones de fórmula y regla), `web` (tableros y selector) | El catálogo de reglas y fórmulas vive en `packages/domain` y se versiona en `db`; no se dibuja como componente de ejecución. |

Los hallazgos **P1** no se representan como componentes porque son decisiones transversales: contratos REST/WebSocket/MQTT (P1-01), frontera de seguridad local (P1-02), backpressure y escritura por lotes (P1-03), geometría y SRID (P1-04), alcance verificable del determinismo (P1-05) y arranque, migraciones y seed (P1-06). Afectan a `api`, `ws`, `ingest`, `db` y `sim`, pero no crean elementos nuevos en esta vista.

## 7. Límites

- **No hay implementación.** No existen la aplicación, el monorepo, los servicios, la base ni datos sintéticos generados. Los componentes son previstos.
- **El MVP es local.** La infraestructura usa Docker Compose (base y broker) y los procesos se ejecutan en local, sin autenticación y sin exposición a internet (ADR-006, NFR-PORT-01). Los recursos cloud son una opción futura, no una arquitectura implementada.
- **Cloud no está dimensionado.** No se eligen proveedor, región, costo, SLA, retención efectiva ni segregación IT/OT. Tampoco se afirma que los recursos cloud estén contratados o probados.
- **No hay diagrama de despliegue.** La vista de componentes no muestra nodos, redes, puertos, réplicas, alta disponibilidad, zonas de seguridad ni separación IT/OT. Tampoco es un diagrama de contenedores: la agrupación “MVP local” es lógica.
- **No hay diagramas de contexto ni de código.** La decisión DL-005 los excluye. El contexto se representa con actores y sistemas externos dentro de la misma vista.
- **Actores simplificados.** Se modelan cinco roles con interacción directa en el MVP. Otros roles del alcance y del SRS no se dibujan como componentes separados; sus requisitos siguen vigentes (FR-DRILL-01, FR-REC-03).
- **Sistemas externos futuros.** FMS, GPS, SCADA, báscula, perforación/voladura y `PlanSource` no están integrados. Los adaptadores son posteriores (ADR-004, D-14).
- **ADR propuestas.** ADR-008 a ADR-014 están en estado Propuesto. El modelo puede cambiar si alguna se rechaza o se sustituye.
- **Sincronización manual.** El DSL y los `.puml` son dos artefactos: el DSL define elementos y relaciones; los `.puml` definen la presentación. Un cambio en uno exige revisar el otro.
- **No sustituye la arquitectura.** El detalle de eventos, tablas, stack y NFR está en [02 — Arquitectura](02-arquitectura.md); este documento solo ubica los componentes y su relación con DDD y las ADR.
